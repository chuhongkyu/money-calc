## 1. 왜 지금

배포된 사이트를 확인한 결과:

| 확인한 것                              | 결과                                           |
| -------------------------------------- | ---------------------------------------------- |
| 사이트맵에 올린 URL                    | 4개 (`/`, `/rules/2026`, `/privacy`, `/terms`) |
| 그중 서버가 서로 다른 HTML 을 주는 URL | **0개**                                        |
| 검색엔진이 볼 실질 페이지              | **1개**                                        |

SPA 라 `index.html` 한 벌이 모든 경로에 그대로 나간다. `useDocumentSeo` 로 경로별 title·canonical 을 나눴지만 **JS 실행 후에 바뀌는 값**이라 한계가 있다. `curl` 로 받으면 여전히 전부 같은 HTML 이다.

그리고 롱테일 검색어(`연봉 3000만원 실수령액`)에 **착지할 URL 자체가 없다.** 결과 화면 `/result` 는 robots.txt 로 막혀 있고, 연봉 구간별 페이지도 없다.

같은 문제가 광고 심사에서도 걸린다. 애드핏 운영정책의 반려 사유 중 "콘텐츠의 내용이 지나치게 부족하여 방문자의 유의미한 콘텐츠 소비가 발생하지 않는 경우" 에 정확히 해당한다.

## 3. 원칙

**제품의 단순함은 건드리지 않는다.** 사용자가 겪는 복잡도(로그인·입력 단계)와 검색엔진이 보는 표면적(URL 개수)은 별개다. 계산기는 지금처럼 "연봉 하나 넣으면 끝" 으로 둔다.

**콘텐츠 페이지는 Stackflow 앱 안에 넣지 않는다.** 읽기 전용 글이라 상태도 라우터도 필요 없다. 빌드 때 정적 HTML 로 뽑아 별도 경로에 둔다.

- 앱 번들 크기에 영향 0
- JS 없이도 완전히 읽히는 HTML
- 검색엔진이 렌더링을 기다릴 필요 없음

**계산 결과를 사실로 게시한다는 뜻이다.** README 의 "정확성이 최우선" 이 여기서 가장 무겁게 적용된다. 6절의 선행 조건을 반드시 먼저 끝낸다.

## 4. 1단계: 연봉 구간별 자동 생성 페이지

글을 쓰지 않는다. `src/rules/` 데이터와 `src/domain/salary/` 계산 함수로 페이지를 만든다.

### URL 구조

```
/salary/3000     → "연봉 3,000만원 실수령액"
```

만원 단위 정수. 사람들이 검색창에 치는 단위(`연봉 3200만원`)와 맞고, 한글 URL 인코딩 문제가 없다.

### 생성 범위

연봉 **2,000만원 ~ 10,000만원(1억)**, **100만원 단위** → **81개**

- 2,000만원 미만: 최저임금 근처라 연봉 단위로 검색하는 사람이 적다
- 1억 초과: 검색량이 흩어지고 개인 편차가 커서 후순위
- 50만원 단위(161개)는 **하지 않는다** — 9절 참고

### 계산에 쓸 고정 조건

페이지마다 계산 조건이 달라지면 안 되고, 화면에 명시해야 한다.

| 항목          | 값                                            | 근거                      |
| ------------- | --------------------------------------------- | ------------------------- |
| 기준 연도     | 2026                                          | `src/rules/index.ts` 최신 |
| 퇴직금        | **별도** (연봉 ÷ 12)                          | 일반적인 계약 형태        |
| 부양가족      | 1명 (본인)                                    | 간이세액표 기본           |
| 8~20세 자녀   | 0명                                           | 〃                        |
| 비과세        | `rules.defaults.nonTaxableMealMonthly` (식대) | 데이터에서 읽음           |
| 원천징수 비율 | 100%                                          | 기본값                    |

### 페이지 구성

```
h1   연봉 3,000만원 실수령액
     ├─ 월 실수령액 (핵심 답, 큰 숫자)
     ├─ 세전 월급 / 총 공제액
     │
h2   공제 내역
     └─ 표: 국민연금 · 건강보험 · 장기요양 · 고용보험 · 소득세 · 지방소득세
        (각 항목 금액 + 요율)
h2   계산 기준
     └─ 위 고정 조건 표 + 간이세액표 버전 + /rules/2026 링크
h2   조건이 다르면 얼마나 달라지나
     └─ 부양가족 2명일 때 / 비과세 30만원일 때 / 퇴직금 포함일 때 (3개 비교)
h2   비슷한 연봉
     └─ ±500만원 범위 인접 페이지 링크 (내부 링크 = 크롤링 경로)

CTA  "내 조건으로 계산하기" → /
JSON-LD  FAQPage
```

"조건이 다르면" 절이 이 페이지를 단순 숫자 나열에서 구분해준다. 같은 계산 함수를 파라미터만 바꿔 3번 더 호출하면 된다.

## 7. 기술 설계

### 프리렌더 방식

**별도 정적 생성 스크립트** (`scripts/build-static-pages.mjs`) 로 간다. React 서버 렌더링도, 프레임워크 교체도 하지 않는다.

가능한 이유가 CLAUDE.md 규칙 덕분이다 — `src/domain/` 이 React·브라우저·Capacitor 를 import 하지 않는 순수 함수라, **Node 스크립트에서 계산 로직을 그대로 재사용할 수 있다.**

```
scripts/build-static-pages.mjs
  ├─ import { calculateSalary } from "src/domain/salary"
  ├─ import { getRuleSet } from "src/rules"
  ├─ 연봉 2000~10000만원 순회
  ├─ 계산 → HTML 문자열 생성
  └─ dist/salary/<만원>/index.html 로 쓰기
```

`pnpm build:web` 뒤에 붙인다.

**Next.js 로 옮기지 않는 이유**

- 이 코드베이스는 웹 + iOS + Android 를 한 벌로 간다 (Capacitor). Next.js 는 Capacitor 와 잘 안 맞는다
- 화면 전환이 Stackflow 기반이라 라우팅을 통째로 다시 짜야 한다
- 계산 도메인·규칙 데이터·테스트는 그대로인데 껍데기만 갈아엎는 꼴

### 생성 HTML 요건

- 본문 텍스트가 HTML 에 그대로 들어있을 것 (JS 없이 읽힘)
- 페이지마다 고유한 `<title>`, `<meta name="description">`, `<link rel="canonical">`
- 앱과 같은 SEED 토큰 CSS 를 쓰되, 인라인 `<style>` 최소한으로 (앱 번들 576KB 를 콘텐츠 페이지가 받을 이유 없음)
- 모바일 우선 레이아웃, 본문 `max-width` 는 앱의 `CONTENT_MAX_WIDTH` 와 맞춤

## 9. 리스크

### 유사 페이지 대량 생성 (doorway pages)

가장 큰 리스크다. 숫자만 다른 페이지 수백 개는 검색엔진이 "관문 페이지" 로 보고 통째로 평가절하할 수 있다.

**대응**

- 100만원 단위 81개로 제한. 50만원 단위(161개)로 늘리지 않는다
- 페이지마다 실제로 다른 정보를 넣는다 (공제 항목별 금액, 조건별 비교 3종, 인접 연봉)
- 자동 생성이라도 페이지당 정보 밀도가 낮으면 의미 없다 — 4절 구성을 다 채운다
- 색인 상태를 Search Console 에서 보고, "크롤링됨 - 색인 생성 안 됨" 이 많으면 범위를 줄인다

### 매년 데이터 갱신

연도가 바뀌면 81개 페이지의 숫자가 전부 바뀐다. `rules/YYYY.ts` 만 고치면 자동 반영되도록 설계하되, **이전 연도 URL 을 어떻게 할지** 는 미결정 (10절).

### 무료 서브도메인

`money-calc-chi.vercel.app` 은 Vercel 소유 존이다. Search Console DNS 확인이 불가능했던 것과 같은 뿌리의 문제로, 애드핏 "매체의 소유관계" 확인에서도 걸릴 수 있다. 다만 **페이지가 1개인 상태에선 도메인을 바꿔도 달라질 게 없다.** 1단계 이후에 판단한다.

## 11. 작업 순서 (제안)

```
0. 골든 테스트 25개 채우고 통과            ← 선행 조건 (6절)
1. vercel.json 정적 파일 처리 확인          ← 막히면 설계가 바뀜
2. scripts/build-static-pages.mjs 골격
   + 페이지 1개만 생성해서 실제 배포 확인
3. 81개 전체 생성 + sitemap 빌드 타임 생성
4. Search Console 색인 상태 관찰 (2~3주)
5. 결과 보고 가이드 글 착수 여부 판단
```

2번에서 **한 개만 먼저 배포해 검색엔진이 실제로 읽는지 확인**하고 나머지를 푼다. 81개를 만들어 놓고 rewrite 에 걸려 있는 걸 나중에 발견하는 게 최악이다.
